# Local lean MCP handler prototype

Approved scope: prototype a leaner handler locally, keep all fourteen tools and security checks, use existing stable installed packages, and stay completely free. Live `/mcp` remains on the checked high-level handler unless later hosted measurement and publication are agreed. No new service, dependency, storage, paid plan or public diagnostic route.

## Evidence and design

The isolated hosted comparison succeeded on 110 calls but reported 1–9 ms for permission-only checks, 3–12 ms for a one-tool handler and 3–41 ms for the full handler. This implicates additional MCP work without proving the spike mechanism. Installed SDK 2.3.1 supports a fresh low-level `Server` from the same Agents `createMcpHandler` factory in both protocol lanes. The high-level `McpServer` recreates fourteen registered-tool objects, executors and closures each request and regenerates list projections. Prototype a low-level server with two request handlers and a reusable immutable public catalogue, using the existing Standard Schema validators. Keep the OAuth wrapper, official transports, body limits, Host/Origin checks and per-operation museum client unchanged. No server instance, client, credential, request, permission, result or I/O promise may be shared.

## Old behavior and failure modes to retain

- All fourteen tools, descriptions, JSON schemas, annotations, capabilities and instructions remain discoverable and equal in both implementations.
- Missing/revoked credentials and repository permission fail closed; warmed public data never confers permission. Concurrent callers stay isolated.
- Invalid arguments, strict research fields, pagination bounds, defaults, unknown tool names and prototype-key names cannot reach an operation. Existing non-strict stripping remains unchanged.
- Both legacy 2025-03-26 and modern 2026-07-28 lanes retain official request/result validation and wire projection. No sessions or server reuse. Unknown methods fail.
- Draft writes retain validation, fresh base revision, expected commit and checked exact preview/publication checks. Sources, uncertainty, credits and separate ledgers remain intact.
- Host/Origin, consent, PKCE, callback replay, audience/resource scopes and credential passthrough protections remain enforced by the unchanged wrappers.
- No dynamic tools, output schemas, parameter-bound headers or per-tool scope challenges are currently used. Fail explicitly if the lean catalogue gains parameter-bound headers without implementing their SDK enforcement; do not silently omit a high-level SDK security feature.

## Steps and verification

1. Add `createLeanMuseumServer` in `auth/mcp/server.mjs`, sharing the existing tool metadata and operation adapter with the baseline. Use official low-level `Server`, current validators and `projectCallToolResult`. Keep `createMuseumServer` as a reference and production default. Add an explicit local-only build selector in `scripts/build-auth.mjs`; reject unknown values.
2. Add parity tests in `test/mcp-lean.test.mjs`: compare entire discovered catalogues/instructions and every operation with deterministic adapters; invalid/unknown/prototype tool names; defaults, strictness, operations never reached for invalid input; errors; concurrent clients. Run existing sourced research and publication invariants against the lean factory too, where practical. Verify negative controls can fail.
3. Extend `scripts/check-mcp-runtime.mjs` only for an opt-in repeatable workload/profile receipt and stronger relevant negative controls. Build both candidates with readable symbols and identical minified settings, run complete compiled OAuth acceptance on each, then bounded workerd CPU profiles in alternating order. Retain sanitized summaries (not raw credentials/HTTP logs). A profiler sample or local elapsed time is not hosted per-request CPU compliance.
4. Assess the measured difference and correctness. If ineffective, retain evidence and leave production unchanged; do not chain speculative rewrites. If promising, report the smallest candidate and limits before proposing a hosted comparison. Run full tests/build with the default baseline, commit/push a small normally checked PR and inspect its exact served preview. The public preview may deploy normally; the live authentication handler must remain baseline.
5. Preserve useful evidence, stop/dispose all task-owned runtimes, remove temporary/build directories after inspection. Keep original museum files untouched. Report local results, live state and any remaining hosted acceptance requirement candidly.

## Local result

The prototype uses the installed official `Server` with two handlers, an immutable public tool catalogue and the same shared museum operation adapter. Discovery, annotations, instructions, all fourteen valid calls, defaults, invalid input text, strict research fields, stripped extra editorial fields, unknown/prototype tool names, concurrent callers and bounded errors match the reference. Sourced coverage, pagination, manager statistics, evidence warnings, stale snapshot rejection and warmed-cache authorization checks run against both factories. The lean protocol also retains actual museum-client publication refusals for missing checks, stale commits/main, extra files, absent served previews and revoked access; a green check remains `publishing` until the served revision agrees.

The lean bundle is written only to ignored `auth/prototype-build/`; the default build and live handler remain baseline. Auth packaging explicitly refuses a non-baseline selector before changing output files, with a negative test. Both minified candidates pass the complete compiled OAuth acceptance in legacy 2025-03-26 and modern 2026-07-28 lanes, including Host/Origin, consent, PKCE, callback replay, revoked access, token passthrough and removed diagnostic routes. No Cloudflare sign-in, live OAuth credential or network service was used for measurements. All upstream calls in the compiled runtime are fixed local fixtures.

Minified guide/discovery workload: three fresh-isolate runs per candidate, each 500 discovery plus 500 guide requests, in baseline/lean/lean/baseline/baseline/lean order. Baseline non-idle self samples: 5,403 / 5,549 / 5,765; lean: 4,853 / 5,164 / 5,101. Mean reduction 9.6%. GC samples averaged 551 versus 336 (39.0% lower). Minified mixed workload: three runs per candidate, each 100 discovery plus 400 guide/manager/statistics/wartime requests in the same alternating order. Non-idle samples averaged 3,716 versus 3,598 (3.2% lower), with overlapping individual readings, including one lean reading slightly above its baseline pair. This is a small exploratory improvement, not evidence of reliable hosted headroom. GC samples averaged 254 versus 239 (6.0% lower). Raw elapsed times varied and include waits; they are not CPU measurements.

One additional readable-symbol capture per handler confirms the intended factories actually execute. The reference contains self samples in `registerTool` (4), `_createRegisteredTool` (56), `createToolExecutor` (1), `setToolRequestHandlers` (3), `convertListedInputSchema` (3) and `createMuseumServer` (12). The lean capture identifies `createLeanMuseumServer` (3), with no sampled tool registration path. Absence of samples is not proof of zero work; the code removes these repeated registry allocations and list projections by construction. Symbol-build GC readings were 552 and 547, showing the variation and why the minified GC reduction must not be generalized. No capture proves the cause of the earlier hosted 41 ms spikes.

Sanitized summaries are in `plans/evidence/2026-10-20-lean-mcp-local.json`. They retain run order, workload labels, sample counts, top function names and limits, with no credentials or request bodies. Reproduce each guide run after building its candidate with `ALBION_CPU_ROUNDS=500 ALBION_CPU_PROFILE=/absolute/output.cpuprofile node scripts/check-mcp-runtime.mjs`; add `ALBION_MCP_HANDLER=lean` for its separate bundle. For mixed runs add `ALBION_CPU_WORKLOAD=research ALBION_CPU_ROUNDS=100`. Build via `node scripts/build-auth.mjs` (default baseline) or `ALBION_MCP_HANDLER=lean node scripts/build-auth.mjs`; `ALBION_CPU_SYMBOLS=1` opts into readable symbols. Run `node scripts/summarize-mcp-profile.mjs /absolute/profile...` for inspectable summaries. Profiling is opt-in, bounded to 1–1,000 workload rounds and keeps normal production settings unchanged.

The parity check initially rejected missing optional `undefined` catalogue fields in the in-memory transport. The prototype now preserves the exact reference catalogue, including those fields; no comparison was weakened. A first full-suite run collided with a simultaneous public-asset rebuild (`ENOENT` while copying a regenerated archive file); verification was rerun sequentially rather than accepting that failed result. Final tests/build and review receipts follow below. Keep this prototype in its review branch; do not merge or activate it as a Free CPU fix. A hosted comparison remains a separate next step if worthwhile, using the same Free account, controlled owner consent and a bounded rollback. No paid plan, new dependency, public diagnostic route or live authentication deployment has been introduced.

Final local verification: all 70 tests and the complete default Astro/compiled OAuth build pass. Both minified prototype and reference builds passed every profiled runtime run; readable-symbol captures passed too. The summarizer's idle-only negative control fails with `An idle-only capture cannot measure the handler.` The prototype remains local-only; no live authentication deployment or billing change was performed. Existing Decap transitive security advisories remain documented in README and outside this handler experiment.
